# farmvalue

MLflow-пайплайн для Kaggle-симуляции Kaggriculture. Реплеи партий превращаются в датасет, на нём обучается модель вероятности победы. Модель проходит через эксперименты и Model Registry и обслуживается сервисом `POST /process`. Отдельно агенты (два моих сабмита и публичные решения) версионируются как модели и сравниваются в round-robin.

```
реплеи Kaggriculture ──> dataset run (parquet + Dataset) ──> EDA run
                                   │
                                   ▼
                  kaggriculture-winprob: runs вариантов модели
                                   │ метрики, артефакты, LoggedModel
                                   ▼
            Model Registry: kaggriculture-winprob v1..vN, @champion
                                   │ загрузка один раз на старте
                                   ▼
                       FastAPI: POST /process

агенты ──> kaggriculture-agent v1..v8 ──> round-robin ──> реплеи ──> датасет v2
```

## Архитектура MLflow

| Сервис | Роль |
|---|---|
| `postgres` | Backend store: эксперименты, runs, параметры, метрики, теги, датасеты, LoggedModel, registry |
| `s3` (RustFS, S3 API) | Artifact store, бакет `mlflow`: модели, графики, parquet |
| `mlflow` | Tracking server и UI, `--serve-artifacts`: клиенты ходят за артефактами через сервер, S3-креды есть только у него |
| `app` | Inference-сервис (профиль `app`) |

Клиентам нужен только `MLFLOW_TRACKING_URI`. Сервер отдаёт артефакты по схеме `mlflow-artifacts:/...` и сам кладёт их в `s3://mlflow/...`. В `.env` стоят `MLFLOW_ENABLE_PROXY_MULTIPART_DOWNLOAD=false` и `..._UPLOAD=false`. Иначе MLflow 3 для S3 выдаёт клиенту presigned-ссылку на `http://s3:9000`, а этот адрес снаружи compose-сети недоступен.

Сущности и связи:

- **Experiment**: `kaggriculture-data` (датасеты, EDA), `kaggriculture-winprob` (модели), `kaggriculture-league` (агенты).
- **Run**: один запуск с параметрами, метриками, тегами, артефактами и входами (dataset inputs).
- **Dataset**: имя, digest (хеш содержимого), source (где лежат данные), schema и profile. Связан с run через input с контекстом `build`, `eda`, `training` или `evaluation`.
- **LoggedModel** (`m-...`): модель, залогированная в run. Метрики на тесте привязаны к ней и к тестовому датасету.
- **Registered Model / Version**: версия ссылается на LoggedModel и через него на run, датасеты и код.
- **Alias**: изменяемый указатель на версию (`champion`, `challenger`). Сервис знает только alias.

## Запуск

```bash
make install
make up
```

UI: http://localhost:5000, консоль S3: http://localhost:9001. Каталог с реплеями задаётся в `.env` переменной `KAGGRICULTURE_DIR`.

Весь путь с нуля:

```bash
make all
```

По шагам:

| Команда | Что делает |
|---|---|
| `make dataset` | реплеи -> `snapshots.parquet`, run `dataset-v1`, Dataset input |
| `make eda` | run `eda-v1`: графики, `summary.md`, корреляции |
| `make train` | 4 варианта модели на v1 |
| `make league SEEDS=6` | регистрация агентов и round-robin |
| `make history` | старая лига проекта (`league/games*.jsonl`) как отдельный датасет |
| `make dataset-v2` | датасет v2 (ladder + партии лиги) и лучший вариант на нём |
| `make register` | baseline и два лучших run в реестр, `champion` и `challenger` |
| `make app` | сервис на http://localhost:8080 |

## Данные

Строка датасета это снимок партии на начало дня d (d = 1..29): публичное состояние обеих ферм, рынка и города. Таргет `seat0_wins`, ничьи и партии с ошибками отбрасываются. Признаки (`src/farmvalue/features.py`): деньги, активы, рабочие, кварталы, растения по культурам, животные, неполитые и неудобренные клетки и разности seat 0 минус seat 1. Тот же код считает признаки в сервисе, так что признаки при обучении и в сервисе не расходятся.

Сплит по `sha1(episode_id) % 5`. Снимки одной партии сильно зависимы, поэтому случайный сплит по строкам дал бы утечку. Хеш стабилен: при добавлении партий в v2 старые не меняют сторону.

**Source, digest, lineage.** Run `dataset-vN` логирует parquet как артефакт, а Dataset с `source = s3://mlflow/<exp>/<run>/artifacts/dataset/snapshots.parquet`, то есть с физическим адресом файла. Digest считается по содержимому датафрейма: v1 и v2 различаются, повторная сборка из тех же реплеев даёт тот же digest. В параметрах run хеш списка реплеев и коммит кода. Обучающий run пишет `training` и `evaluation` inputs с тем же source и тег `data_run_id`. Цепочка: реплеи -> dataset run -> train run -> LoggedModel -> версия в реестре -> alias -> сервис.

## Эксперименты

Основная метрика `test_roc_auc` по снимкам тестовых партий. Вспомогательные: `test_log_loss` и `test_brier`, потому что выход используется как вероятность; `test_accuracy`; `test_roc_auc_early/mid/late` по фазам игры; `cv_roc_auc_mean/std` (GroupKFold по партиям на train); `league_roc_auc` на тестовых партиях лиги из v2.

| Вариант | Идея |
|---|---|
| `baseline_logreg` | логрегрессия на дне и разнице денег |
| `logreg_all` | логрегрессия на всех признаках |
| `hgb_default` | HistGradientBoosting по умолчанию |
| `hgb_tuned` | меньше листьев, больше min_samples_leaf, L2 |

Артефакты каждого run в `diagnostics/`: ROC, калибровка, матрица ошибок, AUC по дням, permutation importance, `metrics.json`.

Все варианты принимают одинаковый вход (полный набор `FEATURES`) и сами выбирают нужные столбцы через `ColumnTransformer`. Поэтому любую версию можно поставить под `champion`, и сервису не придётся меняться.

Результаты (тест v1 общий для всех v1-вариантов, `league_roc_auc` общий для всех):

| Run | test_roc_auc | log_loss | Brier | cv_roc_auc | league_roc_auc |
|---|---|---|---|---|---|
| baseline_logreg-v1 | 0.677 | 0.678 | 0.243 | 0.648 | 0.835 |
| logreg_all-v1 | 0.659 | 0.631 | 0.223 | 0.688 | 0.952 |
| hgb_default-v1 | 0.753 | 0.608 | 0.202 | 0.749 | 0.934 |
| hgb_tuned-v1 | 0.773 | 0.562 | 0.191 | 0.753 | 0.935 |
| hgb_tuned-v2 | 0.807 | 0.525 | 0.177 | 0.787 | 0.979 |

`test_roc_auc` у v2 считается на тесте v2, куда входят партии лиги, поэтому напрямую с v1 его сравнивать нельзя. Сравнимая колонка `league_roc_auc`. В реестре v1 это baseline, v2 `hgb_tuned` на v1 (`challenger`), v3 `hgb_tuned` на v2 (`champion`).

## Агенты

| Агент | Источник | Класс решения |
|---|---|---|
| `g2a` | мой сабмит G2A | G плюс гейт окна сброса |
| `g_mkt` | мой сабмит G | рыночная ветка |
| `multi_route` | публичный ноутбук | выбор маршрута развития фермы |
| `market_smart` | публичный ноутбук | тайминг продаж по рынку |
| `shop_router` | публичный ноутбук | реактивный роутер по магазинам |
| `replay_routing` | публичный ноутбук | проигрывание записанных партий |
| `fieldcraft_2900` | публичный ноутбук | компактная эвристика |
| `starter` | kaggle_environments | нижняя планка |

Каждый агент это pyfunc-модель: исходники как артефакт и обёртка `KaggleAgent` (`predict(observations) -> actions`). Агент загружается так же, как в kaggle_environments: исполняется `main.py` и берётся последний callable. На одном сиде агент из реестра даёт тот же счёт, что и исходный файл. Партии играют модели, скачанные из реестра. Run агента хранит модель и его метрики в лиге: games, score, Wilson CI, BT-рейтинг, средний банк. Run `round-robin` хранит лидерборд, матрицу попарных результатов, кривые банка, несколько реплеев и таблицу партий как Dataset. Alias `champion` у `kaggriculture-agent` ставится на лучший BT-рейтинг.

Round-robin на одном сиде со сменой мест (56 партий):

| Агент | score | BT | средний банк |
|---|---|---|---|
| g2a | 1.000 | 3704 | 115 721 |
| g_mkt | 0.857 | 3059 | 115 701 |
| market_smart | 0.714 | 2472 | 115 071 |
| shop_router | 0.571 | 1883 | 113 557 |
| replay_routing | 0.429 | 1253 | 99 967 |
| fieldcraft_2900 | 0.214 | 415 | 104 800 |
| multi_route | 0.214 | 415 | 72 564 |
| starter | 0.000 | -1201 | 3 980 |

На одном сиде доверительные интервалы широкие, для точного рейтинга `make league SEEDS=6`.

Агенты держат состояние партии в глобалах модуля, так что pyfunc здесь служит упаковкой для версионирования. Stateless serving из него не получится: один загруженный экземпляр соответствует одному игроку в одной партии.

## Сервис

```bash
make app
curl -s localhost:8080/model
curl -s -X POST localhost:8080/process -H 'content-type: application/json' \
  -d '{"observations": [<observation из kaggle_environments>]}'
```

На старте `lifespan` разрешает `MODEL_NAME@MODEL_ALIAS` в номер версии и грузит `models:/<name>/<version>` один раз. Загрузка идёт по номеру, а не по alias: если alias переставят между двумя вызовами, метаданные в ответе всё равно совпадут с весами. `/process` считает признаки и вызывает модель в `asyncio.to_thread`, чтобы не блокировать event loop. В ответе `win_prob_seat0`, `win_prob_player` (если в observation есть `player`) и блок `model` с версией, run_id и model_id. По нему видно, какая версия ответила.

Переключение версии:

```bash
make promote VERSION=1
make app-restart
curl -s localhost:8080/model
```

## Горячее обновление: проблемы и что лучше

Сейчас версия выбирается при старте процесса, и чтобы сменить модель, надо переставить alias и перезапустить сервис. Слабые места:

- Перезапуск это простой или холодный старт: загрузка модели, первые медленные запросы.
- При нескольких репликах alias читается в разное время, и реплики какое-то время отвечают разными версиями.
- Alias меняется в реестре вне деплоя: в git и в манифестах не видно, что поменялось, откат тоже идёт руками через реестр.
- Перезапуск по любой причине (OOM, перенос пода) тихо подхватит новую версию, даже если её никто не выкатывал.
- Старт зависит от доступности MLflow и S3: если они лежат, сервис не поднимется.
- Окружение модели (версии sklearn, skops) может разойтись с окружением сервиса, и ошибка проявится только при загрузке.

Как лучше:

- Деплой пинит конкретную версию (`models:/name/7`) в конфиге, alias остаётся указателем для людей и CI. Смена версии идёт как обычный релиз с ревью и откатом.
- Blue/green или canary: новая версия поднимается рядом, прогревается, получает часть трафика, затем переключается балансировщиком.
- Если нужна смена без рестарта: фоновая задача периодически проверяет alias или получает webhook от реестра (в MLflow 3 они есть), загружает новую версию в отдельный объект, прогревает и проверяет её, затем атомарно подменяет ссылку. Версия пишется в каждый ответ и в метрики.
- Модель запекается в образ на этапе сборки (`mlflow models build-docker` или скачивание артефактов в CI), и рантайм от MLflow не зависит.
- Окружение сервиса собирается из `requirements.txt` модели, либо используется отдельный serving (MLServer, KServe).
